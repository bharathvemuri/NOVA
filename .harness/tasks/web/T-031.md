## Context

004 §19 required an occlusion strategy without defining it; the answered questions fixed both the implementation (drei Html) and the meaning of occlusion (hide when the body is behind another body) plus simple overlap de-cluttering. 004 §19 also warns against embedding astronomical metadata in DOM strings without a defined source — hence label text comes from the bodies endpoint.

## Task

Implement the label layer as a DOM overlay driven by scene positions: per-body anchoring (respecting the Moon's visualization offset), occlusion hiding, deterministic overlap de-cluttering, distance-based scaling, the global toggle and selection emphasis. Source all text from the bodies endpoint.

## Acceptance criteria

- [ ] Labels are DOM elements overlaid on the canvas via drei's Html, not in-scene sprites
- [ ] A label is hidden when its body is occluded by another body (drei occlude), asserted by a test with a contrived occluding configuration
- [ ] Overlapping labels are de-cluttered by a documented deterministic rule (e.g. priority by body then by screen distance), producing the same result for the same camera state
- [ ] Labels scale with distance within documented bounds and remain legible at the home view
- [ ] Labels are toggleable globally and default to on
- [ ] The selected body's label is visually emphasised
- [ ] The Moon's label anchors to the Moon's rendered position, including the 8x visualization override, so it never detaches from the mesh
- [ ] Label text is sourced from the /api/v1/bodies displayName, not hardcoded strings in the component
- [ ] Labels do not intercept pointer events intended for body selection unless the label itself is clicked, and this behaviour is documented
