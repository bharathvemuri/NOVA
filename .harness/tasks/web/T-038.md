## Context

004 §26 and §29 and 001 §36 all say the same thing: measure before optimizing, and implement precision mitigations only after observing a real artifact. 004 §27 makes disposal a hard requirement because the app is designed for long-running time animation. This task is deliberately measurement-first so no agent introduces speculative complexity.

## Task

Profile the rendering and data path against the stated targets, record the figures in the docs, and harden resource disposal with a repeatable leak test covering mount/unmount, frame switching, mode switching and orbit regeneration. Fix leaks found. Introduce optimisations only where a recorded measurement justifies them, and document before/after numbers.

## Acceptance criteria

- [ ] Measurements are recorded for initial load, first render, steady-state frame time/FPS at the home view, API request latency, orbit generation time, and memory over an extended playback session
- [ ] A leak test runs a long simulated playback session with repeated frame switches, mode switches, orbit regenerations and body selections, and asserts renderer.info geometry/texture/program counts and heap usage return to a stable baseline
- [ ] Every renderer disposes geometry, materials, textures, render targets and event listeners on unmount; a mount/unmount cycle repeated N times shows no monotonic growth
- [ ] Measured figures are compared against the 60 FPS desktop target and written into docs; if the target is missed, the shortfall is reported with its cause rather than the target being quietly restated
- [ ] Any optimisation introduced is justified by a recorded before/after measurement in the same document
- [ ] No floating-point precision mitigation (origin rebasing, camera-relative rendering) is introduced unless a measured precision artifact is documented first
- [ ] Astronomical state is not modified by any optimisation, asserted by the existing mode-switch and camera immutability tests still passing
